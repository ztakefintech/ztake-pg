Ztake Order Management API

Create orders, capture UTRs, verify against payments, update status, and receive callbacks.

Base URL

https://ztake.in (replace with your deployment domain if different)

Authentication

🔐 SECURITY UPDATE: All vendor endpoints now require API key + vendor code authentication for enhanced security.
  • API Key (Primary): Authorization: Bearer pk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx — 32 characters after "pk_"
  • Vendor Code (Required): Must be provided in request body or query parameters (format: AA4563)
  • Cross-Validation: API key must belong to the specified vendor
  • Legacy Support: JWT tokens still supported but being phased out
🆕 Security Enhancement: Vendor codes now use human-readable format (AA4563, QX4012, etc.) and are required for all operations to prevent cross-vendor access.

4) Submit UTR

POST /api/v1/orders/{ztakeOrderId}/submit-utr?vendorCode=AA4563

Headers: Authorization: Bearer pk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Body

{ "utr": "214587963214" }

Behavior:

  • Persists UTR on the order.
  • Verifies the UTR against payments for the same vendor.
  • Always syncs the order amount from the payments row (if found).
  • If the payment has payment_status = 'Succeeded', the order is marked Succeeded and a callback is sent.
  • Prevents reuse: once a payment's UTR is checked (checked_status = TRUE), the same UTR cannot succeed again.
  • ⚠️ Duplicate Prevention: Each UTR can only be used for one order. Attempting to use the same UTR for different orders returns 409 error.

Responses

Status Body Description
200 { success:true, verified:false, status:'Pending', code:'PAYMENT_NOT_SUCCEEDED' } UTR found but payment not succeeded yet.
200 { success:true, verified:true, status:'Succeeded', amount: 250.00 } Verified and succeeded; callback sent.
404 { success:false, code:'UTR_NOT_FOUND' } No payment for this vendor/UTR.
409 { error:'UTR already used for another order', code:'UTR_ALREADY_USED' } UTR already assigned to a different order.
409 { success:false, code:'ALREADY_SUCCEEDED' } Order already succeeded.

5) Update Status (sends callback)

POST /api/v1/orders/{ztakeOrderId}/status

Body

{ "status": "SUCCESS|FAILED|PENDING", "utr": "..." }

Maps to DB statuses Succeeded|Failed|Pending and POSTs a callback.

Migration Guide

⚠️ Breaking Changes: If you're upgrading from the previous version, update your API calls to use vendor_code instead of vendor_id.
🆕 New Features: This update includes callback messages and enhanced vendor APIs.

Before (Old Format)

{
  "utr": "690518190930",
  "amount": 100.00
}

After (New Format)

{
  "vendor_code": "AA4563",
  "utr": "690518190930",
  "amount": 100.00
}

New Fields Added

  • Payouts: admin_notes - Callback messages from admins
  • Settlements: admin_notes - Callback messages from admins
  • Recharges: admin_notes - Callback messages from admins

New APIs Added

  • Callback Events API: /api/public/payment-callback for testing
  • Enhanced Vendor APIs: Improved payout, settlement, and recharge management
  • Event Filtering: Filter callback events by type (payment/payout)

Status Mapping

All status displays now use user-friendly terms:

Technical Status Display Status
paid, succeeded, completedSuccess
created, pendingPending
rejected, failedFailed

Payout ID Format

  • Format: PYT + 8 numbers (e.g., PYT13947473, PYT98765432)
  • Examples: PYT12345678, PYT87654321, PYT11223344
  • Auto-generation: If no reference_id is provided, a unique PYT ID is automatically generated
  • Uniqueness: Each payout ID is guaranteed to be unique across the system

Security Requirements

🔐 CRITICAL SECURITY UPDATE: All vendor endpoints now require dual authentication for enhanced security.

Authentication Requirements

  • API Key: Must be in format pk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx (32 characters after "pk_")
  • Vendor Code: Must be provided in request body or query parameters (format: AA4563)
  • Cross-Validation: API key must belong to the specified vendor
  • Headers: Authorization: Bearer pk_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

Security Benefits

  • Vendor Isolation: Vendors can only access their own data
  • Cross-Vendor Protection: Prevents unauthorized access to other vendors' information
  • Multi-Layer Authentication: API key format + existence + vendor ownership validation
  • Audit Trail: Comprehensive logging for all authentication attempts

Error Handling

Error Code Description Solution
401Invalid or missing API keyCheck API key format and existence
403API key and vendor code mismatchEnsure API key belongs to specified vendor
400Missing vendor codeProvide vendor code in request
404Vendor code not foundVerify vendor code exists in system
